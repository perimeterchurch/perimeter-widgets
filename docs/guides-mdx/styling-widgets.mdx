# Styling widgets

Perimeter widgets render inside a **shadow root**, with their styles compiled
through a shared Tailwind preset. Styling one is tokens-first: reach for design
tokens and `@perimeter/ui` components before writing bespoke CSS, and the result
looks right both here in the studio and on the production WordPress page. This
guide covers the model, the rules, and the two facts that bite people who skip it.

## Tokens first

Every color, radius, and font in the system is a **CSS custom property** defined by
`@perimeter/theme`. The Tailwind preset maps utility classes onto those variables —
`bg-primary` is `var(--color-primary)`, `text-fg` is `var(--color-fg)`,
`rounded-md` is `var(--radius-md)`. Style with the utilities and you inherit the
palette automatically, including any per-embed overrides a host page sets.

<Example label="The token palette in use">
  <div className="flex flex-wrap items-center gap-3">
    <Button variant="primary">Primary action</Button>
    <Badge>Tagged</Badge>
    <Card className="px-4 py-3 text-sm text-fg">Surface on the bg token</Card>
  </div>
</Example>

The core tokens (see `/tokens` for the live reference and every default):

| Token group | Examples                                            | Tailwind utilities                       |
| ----------- | --------------------------------------------------- | ---------------------------------------- |
| Color       | `--color-primary`, `--color-fg`, `--color-border`   | `bg-primary`, `text-fg`, `border-border` |
| Radius      | `--radius-sm`, `--radius-md`, `--radius-lg`         | `rounded-sm`, `rounded-md`, `rounded-lg` |
| Type        | `--font-sans`, `--font-mono`                        | `font-sans`, `font-mono`                 |

Never hard-code a hex value or pixel radius. A literal `#2563eb` ignores host
overrides and drifts from the rest of the system; `bg-primary` tracks the token.

## `@perimeter/ui` vs. custom markup

Before building a control from scratch, check whether the design system already
ships it. The current `@perimeter/ui` set: `badge`, `button`, `card`, `combobox`,
`empty`, `icon-select`, `input`, `input-group`, `label`, `multi-combobox`,
`pagination`, `skeleton`, `skeleton-transition`, `sort-select`, `spinner`, `tabs`,
`textarea`.

- **Use a component** for anything it covers — buttons, inputs, cards, tabs,
  loading states. You get the right tokens, focus rings, and hover/active states
  for free, and your widget stays consistent with every other one.
- **Write custom markup** only for widget-specific layout and composition. Even
  then, style it with token utilities (`gap-4`, `text-muted-fg`, `border-border`)
  so it sits in the same palette.

```tsx
import { Button } from '@perimeter/ui/button';
import { Card, CardContent } from '@perimeter/ui/card';

// Custom layout, system components + tokens inside it.
<Card>
  <CardContent className="flex items-center justify-between gap-4">
    <p className="text-sm text-muted-fg">Next service</p>
    <Button variant="primary" size="sm">
      Add to calendar
    </Button>
  </CardContent>
</Card>;
```

## Two facts the parity work pinned down

These come straight from the dev-vs-production parity audit. Internalize them and
your "looks fine in the studio, broken on the live page" surprises mostly vanish.

### 1. Authors write `rem`; the build emits `px`

Widget CSS is authored in `rem` (Tailwind's default — `p-4` is `1rem`), but a host
page can set any root `font-size`, which would rescale every `rem` unpredictably.
So the widget build runs a **rem→px conversion** at the end of the Tailwind chain:
`1rem` becomes `16px` in the shipped bundle. You keep writing normal Tailwind
utilities; the pipeline freezes the sizing so the widget renders identically no
matter what the host's root font-size is. Don't reintroduce raw `rem` values in
hand-written CSS expecting them to scale — they won't, by design.

### 2. The shadow root isolates *most* styles, but inheritable properties leak in

Each widget mounts into a **shadow root**, so the host page's stylesheet can't
reach your elements and your styles can't escape — that isolation is why a widget
looks the same across wildly different WordPress themes. The catch: a handful of
CSS properties are **inherited** and cross the shadow boundary from the host —
`font-family`, `color`, and `line-height` among them. A widget that leaves text
unstyled inherits the host page's font and color, which is why the studio canvas
has a **host-page simulation** background (the measured production values: 19px /
line-height 35px / color `#353535`). Set the type you want explicitly with token
utilities (`font-sans`, `text-fg`) rather than relying on a default, and preview
against the host-sim background before you ship.

## Checklist

- [ ] Styled with token utilities, no hard-coded colors or radii.
- [ ] Used `@perimeter/ui` for every control it covers.
- [ ] Set `font-family` / `color` explicitly so nothing leaks in from the host.
- [ ] Previewed against the host-page-sim background in the canvas.
- [ ] Checked `/tokens` for the override surface a host page can change.
