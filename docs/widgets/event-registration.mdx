# event-registration

The household version of MinistryPlatform's **Event Details & Registration**
widget. One page for a parent event shows its details and one card per
registration section — the parent itself when it sells a registration, plus
every `bp_Related_Events` row (childcare, a spouse section, concurrent
sessions). A signed-in member picks household members into sections, answers
each section's options and custom form, sees a running total, and submits once.
perimeter-api writes exactly the rows the native widget writes; when something is
owed the widget sends the browser straight to Online Giving to pay and confirms
the payment in place when it returns (2026-10-16), so the native **Invoice
Details & Payment** page is out of the flow and kept only as a fallback.

Built for events that use related-event (household) registration — Family
Night, Vision Night + childcare, Bible study + childcare. The native Event
Finder and native details pages stay in place; staff point a parent event here
by setting its `External_Registration_URL` to this page.

## Embed

```html
<script src="https://widgets.perimeter.org/loader.js" async></script>
<div
  data-perimeter-widget="event-registration"
  data-checkout-url="https://www.perimeter.org/event-checkout/"
></div>
```

The page must carry the event in its query string — `?id=<Event_ID>`, the same
parameter the native details widget reads — so a Register link from the native
Event Finder or details page lands here unchanged. Pair the page with MP's login
widget so members can sign in for the household roster:

```html
<script src="https://ministryplatform.perimeter.org/widgets/dist/UserLogin.js"></script>
<mpp-user-login></mpp-user-login>
```

## Config

`src/types.ts` is the source of truth.

| Attribute                 | Required | Default                     | Description                                                                                          |
| ------------------------- | -------- | --------------------------- | ---------------------------------------------------------------------------------------------------- |
| `data-checkout-url`       | No       | perimeter.org `/event-checkout/` | The native Invoice Details & Payment page: the fallback when the widget cannot take the payment itself (`…?id=<Invoice_GUID>`). |
| `data-payment-flow`       | No       | `direct`                    | `direct`: straight to Online Giving and back (below). `native`: hand off to `data-checkout-url`, the native Invoice Details & Payment page. |
| `data-payment-url`        | No       | perimeter.onlinegiving.org `/mp/payments/` | Online Giving's MP payments page (the native `<mpp-checkout>`'s `paymentprocessortargeturl`). |
| `data-mp-widgets-url`     | No       | detected                    | Root of the MP widgets app whose checkout API mints payment tokens; detected from the MPWidgets/UserLogin `<script>` on the page. |
| `data-id-param`           | No       | `id`                        | Query-string key carrying the `Event_ID` (MP's `EventDetailWidgetIdParameterName`).                 |
| `data-event-id`           | No       | —                           | Pin the event instead of reading the query string (studio preview, single-event pages).             |
| `data-invoice-param`      | No       | `id`                        | Query-string key the checkout page reads (MP's `InvoiceDetailWidgetIdParameterName`).               |
| `data-default-image-url`  | No       | —                           | Fallback image when the event has none.                                                              |
| `data-show-map`           | No       | `true`                      | Show "Get directions" when the location has an address.                                              |
| `data-recaptcha-site-key` | No       | Perimeter's public site key | Used only for the guest (signed-out) path.                                                           |
| `data-sticky-top-offset`  | No       | `0`                         | Height in px of a fixed host header, so the phone summary bar sticks below it instead of under it.   |
| `data-api-url`            | No       | `https://api.perimeter.org` | Override the perimeter-api base URL (local dev).                                                     |

## Behavior

- **Sections** — `GET /api/registration/events/{id}` returns each related row in
  `Position` order (the hub itself is never a section; see **Extras**). Each is a tappable
  card whose footer is a blue button, and the whole card is its hit area (2026-09-22). The
  button reads the row's `Button_Text` whenever staff set one (2026-10-16: it overrides every
  default, Dana). Unset, the widget says "I'm Attending" for a section open to adults, "Add a
  student" for a minors-only section with a grade range, and "Add a child" for any other
  minors-only section, since the parent is adding a child, not attending.
  The native widget's `Enable_Label` opt-in question is NOT rendered (2026-09-16,
  Dana: tapping the card is the opt-in); `Instructions` render as the card's
  one-line summary behind "View details". Closed sections say why (not open
  yet, closed, full, cancelled, sold out) and are not tappable.
- **Extras** (2026-10-15) — a product on the hub event itself (`event.extras`, e.g. product
  2099 "Family Night Pizza Order") is a household order, not a session: one card after the
  sections with the product's option groups (checkbox + quantity, exactly as a section's
  options render) and no people picker. Quantities travel in `plan.extras`; the server prices
  them against the purchaser in `quote.extras` and writes one participant row on the hub with
  the invoice lines, so the kitchen counts them like any option. The review and the
  confirmation list the order under the people; the phone summary bar names it; an order
  with nobody registered is a valid submit. A purchaser who already holds a hub participant
  sees the server's "already have an order" message on the card. Decided by Dana over a
  separate child event ("noise in the database, confusing to the registering user").
- **Section headings** (2026-09-17) — when staff fill `bp_Related_Events.Section_Group`
  ("Adults", "Kids", "Childcare"), the cards are listed under those headings, ordered by each
  group's lowest `Position`; ungrouped sections (and the hub's own section) come first with no
  heading. Grouping happens only when staff set it — nothing is inferred from the audience —
  so an event with the column blank looks exactly as before. Names are matched case-insensitively.
  Each group sits on a tinted band (`bg-muted/40`) that bleeds to the widget's edges on phones
  and sits inside the column from 768px, so the boundary between groups is visible even when a
  single card fills the screen. The heading is serif, sized like the event title (2026-09-22),
  and the band has no border (2026-09-22: the tint alone separates the groups).
- **Who can go where** — `GET …/roster` returns the household with per-section
  eligibility. `Show_Household_Position_ID` and `For_Gender_ID` filter members;
  **`Minor_Registration = 1` lists only children**, `0`/blank lists everyone.
  **Audience rules on the Event** (2026-09-15): `Registration_Min_Age` / `Max_Age` (years on
  event day), `Registration_Min_Grade` / `Max_Grade` (Pre-K–12), gender and household position.
  Adults-only sections offer only adult relationships when adding someone. The cards carry no
  audience, age or grade badges (2026-09-22: the section titles already say who and which
  grades), only status ones ("N spots left", "Closed"), so put the grades in the title;
  grade-bounded sections show a **Grade** select, prefilled from the child's graduation
  year, and never ask a child whose age rules the grade out. Ineligible members read "too young",
  "too old" or "not this grade".
  **Room placement from Event_Rooms** (2026-10-15): a section whose event has `Event_Rooms`
  rows naming a group with `Placement_*` rules (`section.rooms`) places the child from their
  birth date (and grade only where rooms overlap), shows "Room: SEC 1 year olds — from Max's
  birth date" as a line, and never offers a room choice; the product's own room options are not
  shown. A child nothing fits, or whose fits are full, is refused in the drawer and by the quote
  (`NO_ROOM` / `ROOM_FULL`, with the event contact), and the picker reads "no room for this age"
  when the roster already knows. Capacity is `Event_Rooms.Checkin_Capacity` (blank = unlimited);
  two rooms that both fit go to the one with more seats left, then the lower `Balance_Priority`.
  The server re-derives on every quote and submit and stamps the room on the participant.
  **Room placement through option prices** (2026-09-15, events without ruled rooms): when an
  option group's rooms carry `Placement_*` bounds on the Group record, the widget places the
  child from their birth date (and grade when a room asks for it), shows the room as a line
  instead of radios, and the server re-derives it on every quote and submit. The radios return
  only when no room fits, two fit, or the fit is full.
  In a minors-only section the editor also shows a required **Date of birth** for the chosen child, prefilled from their record. The confirmed date is sent with the registration; the API requires one and writes a correction back to the child's contact, so a birth-date question on the custom form is redundant and can be removed.
  Someone already registered in a section's event is grayed out (blocked, not
  warned). Children show their age so parents can pick the right grade band.
- **Card price** (2026-10-15) — a card advertises the least a person pays: `Base_Price` plus the
  cheapest offered choice in each required option group, shown as "from $X per person" when
  options can add to it. A $0 product with only optional paid add-ons says "Paid options
  available"; a free card shows no price block at all (no "Free · no charge", Dana 2026-10-15:
  once the pizza order made Family Night a paid event, every $0 session card had started saying
  it). Before this the card read `Base_Price` alone, so a $0 product with $12 required options
  said "Free".
- **Free events show no prices** (2026-09-15) — when every section is free, offers no deposit and
  every option is $0, the "Free" badges, per-person amounts and the Total row are hidden. Any
  paid section or option brings them all back.
- **Prefill from the record** (2026-09-15) — form fields mapped to an attribute on the Form
  Field (`Add_Attribute_ID` / `Add_Attribute_Type_ID`, the same mapping Kevin's routine writes
  from) open with the child's current attribute as the answer: Toilet Training, Walking Status
  and Allergies for TOP Childcare. A note under the form says where it came from; the parent can
  change anything and only what they confirm is submitted.
- **Several people at once** (2026-09-15, drawers 2026-09-16) — the picker is a set of
  checkboxes and each ticked person answers right under their own name. Ticking opens that
  person's drawer (birth date, grade, resolved room, options, form questions) and collapses
  any other. The drawer opens even when the record already answers everything (prefill), so
  the parent reads each answer beside its question (2026-10-02); only a section with nothing
  to ask collapses straight to a ready row. "Done" re-checks and collapses to a summary row
  that keeps the question with each answer ("Grade: 7th · Allergies: No ✓ Change"); an
  unfinished one shows "Needs answers". Saving reopens the first drawer with a problem. One button adds
  them all; a sole eligible member is pre-ticked. A "Copy …'s answers" button copies the
  previous person's form answers. Editing an existing registration stays single-person.
- **Add a family member** — a signed-in member may add someone not yet in MP;
  the contact and participant are created inside the submit, in their household.
- **Guest path** — signed out, and only when neither the event nor any form
  forces login, a visitor registers themself through the blank form (reCAPTCHA
  verified server-side). Household features need the login widget.
- **Pricing** — `POST …/quote` prices the draft on every change: base price,
  option groups (required / mutually exclusive / quantities / sold out), promo
  codes, deposits. The total shown is the server's, and submit refuses with a
  refreshed total if anything changed in between.
- **One session per person at a time** (2026-10-15, was a warning) — a household member already
  in the draft for a section whose event runs at the same time is disabled in the picker ("in
  another session at this time"); the server refuses the plan with `TIME_CONFLICT` either way,
  and a member already registered for a concurrent event comes back from the roster as
  `time_conflict`. The hub's own event (extras) never conflicts.
- **Submit** — `POST …/submit` with an `Idempotency-Key`; a retry after a network
  blip replays the same result. When the invoice total is above $0 the widget takes the
  payment itself (see **Payment**); the registration is *Awaiting Payment* until it pays, and
  MP releases unpaid seats after about an hour. When it
  is $0 (2026-09-16) the widget stays put and shows "You're registered" with the people and
  sessions — the checkout page would only show a $0 invoice. It says nothing about a
  confirmation email (2026-10-02): each section's `Registrant_Message` template decides
  whether one is sent and to whom, and the widget cannot see either. The
  confirmation ends there (2026-10-02): no "Register someone else" / "Back to events"
  buttons, since the family registered in one pass and the page is reached by direct link;
  a muted "Forgot someone? Add another family member" link brings the cards back.
  `data-return-url` is gone with the button.
- **Payment** (2026-10-16, Dana: a payment state in this widget instead of the native
  Invoice Details & Payment page) — the first build (0.2.10) was pulled the same day: with it,
  Online Giving's payments page spun forever for visitors and their network was then blocked by
  Online Giving's bot detection (403 on every onlinegiving.org host). The native checkout page
  loads Online Giving's `assets/mpsso.js`, which fires a credentialed `GET
  <og>/donate/silent_sso?mp_token=jwt:<mpp-widgets_AuthToken>` before the hand-off; this widget
  did not (0.2.10). Since 0.2.11 the direct flow performs that same silent sign-on itself, right
  before leaving, and also appends `mp_token=jwt:<token>` to the payments URL (the parameter
  mpsso.js adds to every onlinegiving.org link a signed-in member clicks); a guest gets neither.
  Unverified against Online Giving as of 2026-10-16; `direct` stays the default because the page
  is not public yet (Dana) and the first real payment is the test. The mechanics: nobody's widget collects the card, MP's included: the
  native page is a shell around MP's widgets Checkout API (`/Api/CheckoutApi/*`, read from
  `widgets/dist/Checkout.js`), and the card form lives on Online Giving's hosted page. This
  widget makes the same calls (`src/lib/mp-checkout.ts`), with the member's
  `mpp-widgets_AuthToken` or none for a guest. After a paid submit it asks
  `BuildPaymentRequestToken` for a signed token (invoice GUID, Online Giving's URL, this
  page's bare URL as the return address, the full balance, `paymentOption=full`), saves a
  record of the invoice and what was registered in localStorage (`src/lib/pending-payment.ts`,
  24 h), and sends the browser to `data-payment-url?token=…`. Online Giving returns to the
  bare page URL with `?token=<response>`: the widget recovers the event from the saved record
  (the return URL has no `?id=`), posts the response to `ProcessPaymentResponse` (form field
  `text`, `x-csrf-token` from `/Home/CSRFToken`) — this is what writes the `Payments` row and
  sends MP's receipt — strips the token from the URL so a refresh cannot post it twice, and
  shows "You're registered · Payment complete" with the saved people and sessions. MP's
  "received but not yet notified" answer shows "Payment received" with a note that it can take
  a few minutes; a refusal shows "Payment not completed" with Try again (a new token for the
  same invoice), the native page, and Start over. A visitor who backs out of Online Giving
  (browser back, empty draft) sees "You have a registration waiting for payment" with Pay now
  in place. The native page stays as the fallback whenever the widget cannot do this: no MP
  widgets `<script>` on the page (or `data-mp-widgets-url`), `data-payment-flow="native"`,
  the API refusing the token, or an invoice that asks for a deposit (the amount choices live
  on the native page). MP's CORS allowlist admits the page origin (www.perimeter.org), not
  localhost, so local embeds always fall back. The API is MP-internal and undocumented; its
  shapes were read from the bundle, not a spec.
- **Coming back** — the native checkout's "Make Changes" returns with
  `?id=<eventId>&invoiceid=<guid>`; the widget offers that invoice's payment page (it does not
  know the amount owed, so not in place) or a start over.
- **Not supported** — File Upload form fields (a required one closes the
  section), secondary households, and form fields that also write attributes or
  opportunity responses (answers are stored; the side effect is not).

## Layout

Designed phone-first (2026-09-16) after the Great Wolf Lodge "Packages" pattern, then widened.
Container-query thresholds are written in px (`@min-[480px]:`, `@min-[768px]:`) because the
build's rem→px rewrite does not touch `@container` params.

| | Phone (< 480px) | Tablet (480–767px) | Desktop (≥ 768px) |
| --- | --- | --- | --- |
| Hero | full-bleed 16:9 image, description clipped behind "Read more" | same | `max-h-80` image, full description |
| Summary | sticky bar at the top: count badge, total when prices show, chevron opens the review | same | review box below every section (2026-09-22) |
| Sections | one list in `Position` order; tappable cards, picture on top, with status badges, title, "View details", price and the blue add button | same | one card per row, picture beside the copy (2026-09-22) |
| Editor | bottom sheet (`<dialog>` + `showModal()`, top layer) | same | inline in the card |
| Contact | inside the summary bar's expanded panel, under the total ("Contact for this registration": name · email · phone, Edit); the bar opens itself when email/phone or a required address is missing | same | inside the review box, between the total and the submit |
| Submit | sticky bottom CTA: "Add someone to continue" → "Continue to your details" (guests) → "Fix N issues" → submit | same | button in the review box |

- **Contact for this registration** (2026-09-16) — part of the review (who gets the receipt
  sits with the total and the submit), not a card among the events. Signed in, the purchaser's
  name, email and phone from MP show as one line with an Edit button; the fields appear only
  on request or when the record lacks email/phone or the quote requires an address. The
  "update my record" opt-in appears once something has changed and defaults to on. Guests
  give their name, email and phone inside the editor on their first add ("Your details");
  the line then shows what they entered. Wording avoids "Registering as": the purchaser is
  usually not the one attending.
- **Card images** — `/api/event-image/{Event_ID}` for the section's own event, then the hub
  event's image, then `data-default-image-url`; when all three fail the card drops the picture
  and keeps a navy left rule (`data-slot="section-card-noimage"`). Child events without an
  image all show the hub image, so give each a picture in MP to tell them apart.
- **The sheet** sits in the browser's top layer, so a host page's fixed header or a
  `transform` on a wrapper cannot trap or cover it. While it is open the host body is
  scroll-locked, Escape and the backdrop close it, and focus returns to the button that opened
  it. Its "Add to registration" row sticks to the sheet's bottom edge with safe-area padding.
- **Sticky bars are `position: sticky` inside the widget**, so a host ancestor with
  `overflow: hidden` turns them static (see `packages/embed-lab/pages/narrow.html`), and a
  fixed host header needs `data-sticky-top-offset` or the summary bar slides under it.
  Safe-area padding at the bottom needs `viewport-fit=cover` on the host's viewport meta.
- **As few buttons as possible** — the card is the control (the footer button's hit area is
  stretched over the card; screen readers hear "I'm Attending" described by the section's
  title, since several cards say the same thing); the sheet has a close X and its
  save button, no Cancel; the CTA is one button. Edit/remove icons and "View details" are the
  only other controls.
- **Blue buttons have white text** (2026-09-22, by request, knowingly below AA contrast on
  this light blue): `src/styles.css` sets `--color-primary-fg` on the shadow tree's top-level
  elements, because the runtime's token sheet sets navy on `:host` and loads after the widget's
  CSS. The theme package itself keeps navy.
- **Touch targets** are at least 44px on phones: the card button, submit, the edit/remove
  icons, checkbox and radio rows, "View details", the sheet's close button.
- **Tests** — `tests/app.test.tsx` runs the desktop branch (jsdom reports a 0px width, which
  the breakpoint hook treats as "not measured"); `tests/mobile.test.tsx` pushes 343px through a
  controllable `ResizeObserver` mock and covers the bar, the CTA states, the sheet and the
  image chain.

## Testing it locally

Writes are refused by perimeter-api unless its `REGISTRATION_*` guard allows the
event — dry runs included — so local testing needs a hidden test event on the
allowlist. `pnpm embed-lab` → `local-event-registration.html?id=<Event_ID>`
against a local perimeter-api on :5500; set `mpp-widgets_AuthToken` in
localStorage to see the household roster.
