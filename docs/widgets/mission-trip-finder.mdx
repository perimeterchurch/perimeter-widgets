# mission-trip-finder

A responsive card grid of open **GO Journey** mission trips, plus a detail view
for each one. Cards show the destination banner, trip name, destination, travel
dates, the per-participant fundraising goal, and an optional description; trips
at capacity and invitation-only trips are badged.

Clicking a card opens that trip's detail **in place**, without leaving the
page. The detail follows the 2026 Figma redesign, in bands:

1. **Heading** — trip name, destination and travel dates, centred on white.
2. **Photo scroller** — a full-bleed horizontal row of square photos.
3. **About the Journey** — the long-form write-up and the two calls to action.
4. **Hear From Others** — testimonials on the brand navy surface.
5. **Meet the Team** — the roster as darkened squares that brighten on hover.
6. **Donation disclaimer.** Rebuild of the legacy `reactwidgets`

Clicking someone in the roster opens their **GO Journey Participant** page in
place: the trip heading and photo scroller stay, and everything below them is
replaced by that person's photo, fundraising progress, support letter and a
"View Trip Details" button back to the trip.
MissionTripFinder and the legacy `MissionTripDetails` HTML widget
(`api_custom_Mission_Trip_Finder_Widget` and
`api_custom_Mission_Trip_Detail_Widget`) on the perimeter-api backend.

Trips are sorted by travel date and, by default, limited to campaigns that are
still open and marked for the website in Ministry Platform.

## Embed

```html
<script src="https://widgets.perimeter.org/loader.js" async></script>
<div data-perimeter-widget="mission-trip-finder"></div>
```

### As a details page

`data-trip-id` pins the widget to one trip: it renders that trip's detail alone,
with no grid behind it and no Back button. This is what a dedicated
go-journey-details page embeds, so the same bundle serves both surfaces and
existing `?id=` links keep working.

```html
<div data-perimeter-widget="mission-trip-finder" data-trip-id="958"></div>
```

## Navigation and deep links

The open trip lives in the URL as `?trip-screen=detail&trip-id=<id>`, so a trip
is a shareable link and the browser back button steps out of the detail. The
detail view carries a **Copy link** button for exactly that. Keys are prefixed
`trip-` so two embeds on one page never collide.

A `data-trip-id` embed never writes to the URL — the host page owns it.

## Config

The widget reads its config from `data-*` attributes on the placeholder div.
`src/types.ts` holds the zod schema (the source of truth for options and
defaults).

| Attribute                | Type    | Default                                | Description                                                                       |
| ------------------------ | ------- | -------------------------------------- | --------------------------------------------------------------------------------- |
| `data-show-description`  | boolean | `true`                                 | Show the trip's description text on the card.                                     |
| `data-show-cost`         | boolean | `true`                                 | Show the per-participant fundraising goal **on the card**. The detail never shows it. |
| `data-show-spots`        | boolean | `false`                                | Show remaining spots (e.g. "3 spots left") on trips that have a cap.              |
| `data-hide-full`         | boolean | `false`                                | Hide trips at capacity instead of badging them "Registration Full".               |
| `data-include-past`      | boolean | `false`                                | Include closed trips (default shows open GO Journeys only).                       |
| `data-destination-id`    | number  | —                                      | Filter to one destination (MP Journey Destination ID).                            |
| `data-keyword`           | string  | —                                      | Search trip names, destinations, and descriptions.                                |
| `data-max-trips`         | number  | —                                      | Cap the total number of trips shown.                                              |
| `data-trip-id`           | number  | —                                      | Render one trip's detail alone, with no list behind it.                           |
| `data-full-bleed`        | boolean | `true`                                 | Let the photo scroller and testimonial band span the full page width. See below.  |
| `data-gallery-urls`      | string  | —                                      | Comma-separated image URLs for the photo scroller. See below.                     |
| `data-show-testimonials` | boolean | `true`                                 | Show the "Hear From Others" band.                                                 |
| `data-pledge-id`        | number  | —                                      | Open straight to one participant's page. Pairs with `data-trip-id`.               |
| `data-participant-support-url` | string | onlinegiving.org form 1385 | Destination of the participant "Support" button. `{id}` and `{pledgeId}` are replaced.               |
| `data-show-team`         | boolean | `true`                                 | Show the "Meet the Team" roster on the detail view.                               |
| `data-register-url`      | string  | mission-trip-application page          | "Register to Join" destination. `{id}` is replaced with the trip ID.              |
| `data-support-url`       | string  | onlinegiving.org form 1385             | "Support Journey" destination. `{id}` is replaced with the trip ID.               |
| `data-participant-url`   | string  | —                                      | Link each team member somewhere. `{pledgeId}` and `{id}` are replaced.            |
| `data-disclaimer-text`   | string  | the standard donation disclaimer       | Text at the foot of the detail view. Empty string hides the block.                |
| `data-details-url-base`  | string  | —                                      | Link cards OUT to this URL instead of opening the detail in place. See below.     |
| `data-empty-message`     | string  | `No mission trips are open right now.` | Message shown when the list has no trips.                                         |
| `data-default-image-url` | string  | —                                      | Fallback banner for trips whose destination has no artwork.                       |
| `data-api-url`           | string  | —                                      | Override the perimeter-api base URL (advanced).                                   |

Beyond these filters, the endpoint always restricts to GO Journey pledge
campaigns (`Pledge_Campaign_Type_ID = 2`) that are marked `Display_On_Website`
and — unless `data-include-past` is set — have not closed.

### The CTA options are templates, not base URLs

`data-register-url`, `data-support-url` and `data-participant-url` substitute
`{id}` / `{pledgeId}` anywhere in the string rather than appending to the end.
The giving form needs its `#!/` fragment **after** the campaign ID, which
appending cannot express:

```
https://perimeter.onlinegiving.org/donate/form/1385?mp_campaign_id={id}#!/
```

"Register to Join" is dropped automatically on trips that are full or
invitation-only — registering for either is a dead end. "Support Journey" stays.

`data-participant-url` is unset by default, and team cards are then plain
content rather than links. The legacy template wrapped them in a placeholder
`href="insert link"` that was never wired up to anything.

## Data source

`GET /api/mission-trips` for the list and `GET /api/mission-trips/{id}` for the
detail (perimeter-api). Each trip is an MP `Pledge_Campaigns` row of type 2,
joined to `Journey_Destinations` for the destination name and banner image. The
"registration full" state comes from a roll-up of the campaign's `Pledges`
against `Maximum_Registrants` — MP has no registrant-count column, so the API
counts pledges in a seat-holding status (Active or Completed). See
`docs/domains/missions.md` in perimeter-api.

The detail adds two fields the list does not carry:

- **`longDescription`** — `Pledge_Campaigns.Long_Description`, authored in MP's
  rich-text editor. It is **HTML**, unlike the plain-text `description` on the
  card, and is sanitized with DOMPurify before rendering.
- **`participants`** — the team, from the campaign's seat-holding pledges. Each
  is a display name and a `pledgeId`; photos come from
  `GET /api/mission-trips/{id}/participant/{pledgeId}/image`, which 404s for the
  many people with no photo on file, so an avatar falls back to a person glyph.

Banner images are absolute URLs on the destination record (an external CDN), not
served by perimeter-api. A trip whose destination has no banner falls back to
`data-default-image-url`, then to a globe placeholder.

### The full-bleed bands

The photo scroller and the testimonial band escape the host page's content
container and span the whole page. They are **measured** rather than sized with
`width: 100vw`: `100vw` includes the vertical scrollbar, which is ~15px of
horizontal overflow on any page that does not set `overflow-x: hidden`, and the
usual `calc(50% - 50vw)` idiom assumes the embed is horizontally centred in the
viewport.

The breakout stops at the nearest ancestor that clips — anything whose
`overflow` is not `visible`, or which establishes a containing block with a
`transform`. Such an ancestor would clip the band anyway, so bounding to it
means the band fills exactly the space it can occupy and its centred contents
stay centred on what the reader actually sees.

Set `data-full-bleed="false"` for an embed in a sidebar or a narrow column,
where page-wide bands would overwhelm the rest of the page.

### The photo scroller

Ministry Platform has **no per-trip gallery today**, so the scroller is fed by
`data-gallery-urls` (comma-separated). With none set it falls back to the
destination's banner image on its own — the one real photo every trip has, and
the one the pre-redesign hero displayed. With no banner either, the scroller
does not render.

MP does have the right shape, unwired: `Journey_Files` holds `Link` and
`Thumbnail_Link` per file and joins through `Journey_Contents`, but every live
campaign has a null `Journey_Content_ID`, so nothing reaches it (the rows that
exist are old demo data, one of them another church's sample banner). If Global
Outreach starts populating it this becomes an API-backed list without the
component changing shape.

The native scrollbar is hidden, so a circular chevron button sits over the
right edge as the affordance. It advances by exactly one tile, keeping the
scroll-snap points aligned, and wraps to the start at the end — with no
scrollbar and only a forward control, stopping dead would leave a mouse user
with no way back. It is not rendered at all when the photos do not overflow,
since an arrow that cannot move is worse than no arrow, and it honours
`prefers-reduced-motion` by jumping rather than smooth-scrolling.

The scroller is also a labelled region with a tab stop, so a keyboard user can
arrow through the photos — without that the overflow is unreachable for them.

### The participant page

Replaces the legacy `/go-journey-participant/?pledge=<id>` page. A dedicated
page embeds it the same way the trip page does — read `?pledge=` from the host
URL and pass it in as `data-pledge-id`, alongside `data-trip-id`. Inside the
finder it is a URL state (`?trip-pledge=<id>`), so it is a shareable deep link
and browser-back steps out of it.

`data-participant-url` still takes precedence: set it and roster cards link out
to a separate page instead of opening the participant view in place, the same
way `data-details-url-base` works for trip cards.

Two things come from live MP fields the legacy page got wrong:

- **The letter is `Pledges.Letter`.** The old stored proc read
  `Journey_Members.Letter`, and that table has no rows for any current trip, so
  the legacy page would have shown nothing. Most participants have not written
  one; the page renders fine without it.
- **Progress is real.** `raised` is summed from `Donation_Distributions` and
  `goal` is the campaign's per-participant `Fundraising_Goal`. The legacy
  template read a dataset its proc never returned, so its bar was always empty.

The bar is a real `<progress>` element rather than a pair of divs, so it is
announced with its value and maximum ("$1,150 raised of a $2,210 goal"). It is
omitted entirely when the campaign has no goal — there is nothing to measure
against.

### Vertical rhythm

Every band carries the same 120px above and below (stepping down to 64px on
narrow embeds), and the gap between a band's own children is a uniform 64px.
Two deliberate exceptions, both from the Figma: the photo scroller has no
vertical padding at all, so it sits flush against the bands either side, and
the heading's three lines are one tight cluster rather than three children.

That means adjacent bands are 240px apart while the scroller's neighbours are
120px — the scroller's flush edges are what create the difference.

### Testimonials

**The testimonials are hardcoded placeholder copy**, in
`src/lib/testimonials.ts`. MP has nowhere to put them: there is no testimonial
or story table, and nothing on `Pledge_Campaigns` holds free text per person.
They were requested hardcoded so the band could be reviewed while a real source
is decided.

Each card shows an initials monogram rather than a photo. The names are the
Figma's placeholder copy rather than real people, and there are no headshots to
source — inventing faces to go with invented quotes would be worse than
initials. A real source can swap the monogram for a photo without touching the
layout.

The Figma screenshot shows a `2 / 5` pager over this band. That is Figma's own
presentation-mode frame counter, not a carousel control, so every testimonial
renders rather than being paged.

### Square corners

The widget zeroes the three radius tokens (`themeOverrides` in `src/widget.tsx`),
because Perimeter's design language has no corner radius — the cards, hero and
team photos are already rectangles. That flattens every `@perimeter/ui`
component it renders (Button, Skeleton, the message boxes) from one place.
Status badges are untouched: they use `rounded-4xl`, which is not one of those
tokens, so a pill still reads as a pill. A host page's `data-theme-radius-*`
still wins if an embed ever needs a radius back.

> **Changed in 0.2.0:** `data-details-url-base` used to default to the
> go-journey-details page, so every card linked out. It now defaults to unset,
> and a card opens the widget's own detail view instead. Set it to restore the
> hand-off to a separate page.

> **Not ported:** the legacy detail page embedded a Google Map of the
> destination, keyed with an API key committed to a public repo. The map is
> dropped rather than re-keyed — the destination name is already on the page.

> **One deliberate deviation from the Figma:** it draws the two CTAs as white
> text on the `#60bbe9` brand accent, which is about 2:1 contrast and fails
> WCAG AA. The buttons use the theme's `primary`/`primary-fg` pair instead —
> the same `#60bbe9` fill with brand-navy text, 7.3:1. The token comments and
> `packages/theme/tests/contrast.test.ts` both exist to hold that line.
