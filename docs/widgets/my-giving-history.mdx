# my-giving-history

Shows the signed-in user's **household giving history** — a chart of giving by
year, plus a filterable, downloadable table of every gift. It is the
new-architecture rebuild of the legacy `MyGivingHistory` React widget.

Each row is one **donation distribution** (a single program split of a gift), so
a gift spread across multiple programs appears as multiple rows. Columns: date,
donor, program, payment type, and amount. The user can filter by year, donor,
payment type, and program, and download the filtered rows as CSV.

## Foundation gifts (soft credits)

Gifts that reached Perimeter through a foundation, donor-advised fund, employer
match, or IRA custodian are recorded in MP against that organization and
**soft-credited** to the member. The history includes both halves of that
model, so these gifts appear alongside gifts the household gave directly.

Donors know these as **"Foundation checks"** and scan the Donor column for the
foundation's name, which is how the legacy `MyGivingHistory` widget listed
them. So a soft-credited row is **listed under the organization**, with the
member it counts for on a second line:

| Date | Donor | Program |
| --- | --- | --- |
| 8/5/2026 | Fidelity Charitable Gift Fund Foundation<br />_credited to Dennis Lee_ | FRONTIER Campaign |
| 7/19/2026 | Dennis Lee | Tithes & Offerings (Fund) |

The `donorLabel()` helper in `src/lib/format.ts` is the single source of that
choice — the Donor column, the **Donor filter's options**, and the CSV all read
from it, so they can never disagree about what a row is filed under. Filtering
by a foundation therefore also redraws the year chart, which is how to see
"giving through this fund by year" without a separate control.

The CSV carries both: **Donor** (the organization, or the member on a direct
gift) and **Credited To** (always the member). Both are always populated, so a
blank never reads as missing data. The underlying API field is
`softCreditSource` (`string | null`).

The member stays named on every row because the row's donor is not always the
row's giver: for an **IRA distribution (QCD)** the custodian — Fidelity
Brokerage Services, Charles Schwab, Morgan Stanley, Merrill Lynch — is only the
conduit, and the member is the actual donor. MP has no field distinguishing a
QCD from a DAF grant today (`Donation_Sources` is unused and nothing carries a
QCD marker), so the widget cannot label them differently. If that distinction
is ever needed for receipting, it has to start as a classification in MP.

## Authentication

This widget requires a signed-in Ministry Platform user (`auth: 'required'`).
The host page must already hold the user's MP session — the runtime reads the
token from `localStorage` (`mpp-widgets_AuthToken`) and the API client forwards
it as a bearer token to `GET /api/giving/history`. Until a token is present the
widget shows a "Please sign in to use this widget." prompt; the endpoint derives
the household entirely from that token, so a user only ever sees their own
household's giving.

## Embed

```html
<script src="https://widgets.perimeter.org/loader.js" async></script>
<div data-perimeter-widget="my-giving-history"></div>
```

## Config

The widget reads its config from `data-*` attributes on the placeholder div. See
`src/widget.tsx` for the zod schema (the source of truth for available options
and defaults).

| Attribute    | Type   | Default              | Description                  |
| ------------ | ------ | -------------------- | ---------------------------- |
| `data-title` | string | `My Giving History`  | Heading shown above the data |

## Data

Backed by `GET /api/giving/history` in perimeter-api (authenticated, giving
domain). The widget consumes it through the `useGivingHistory` hook in
`@perimeter/api-hooks`.
