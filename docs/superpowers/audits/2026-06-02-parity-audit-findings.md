# Parity Audit Findings — 2026-06-02

**Verdict in one paragraph:** Two CSS-pipeline divergences are confirmed and **user-visible**, and they account for essentially all of the real (non-environmental) dev/prod mismatch. **H2 is the headline and the biggest fix:** the per-widget `tailwind.config.ts` `content` globs omit `packages/ui/src`, so utility classes used *only inside* `@perimeter/ui` components are silently dropped from the shipped bundle while the studio (whose Tailwind scans `packages/ui/src`) renders them — 244 such selectors are missing from `example`'s bundle and 145 from `sermons`' (`css-pipeline-example.md`, `css-pipeline-sermons.md`). **H1 is real but benign-by-design:** the prod build runs a rem→px PostCSS plugin the studio lacks, so every spacing/size value ships as `px` in prod and `rem` in dev (2 affected declarations in `example`, 115 in `sermons`); combined with the confirmed inheritance finding (**H4**) that the host page's 19px body `font-size` pierces the shadow root, any residual `rem` value would scale against the host, but the rem→px plugin is precisely the mechanism that *prevents* that in prod — the divergence is that the **studio doesn't apply it, so the studio is the inaccurate surface**, not prod. **H3** (component gallery) is a confirmed structural divergence but is a dev-only introspection surface with no prod analog, so it cannot mismatch a shipped render — it only misleads the developer. **H5** (React dev/prod + StrictMode) and **H6** (config `configOverrides` seam bypassing zod coercion/validation) are confirmed **behavioral-only** — no rendered-output difference — but H6 is high-attention because the studio can mask prod-only `z.coerce.number()`-class crashes. The visual probe is dominated by canvas-width offset (688px studio vs 1100px fixture) and live-API data/image variance, so its ratios (1.02% example / 54.07% sermons) corroborate but do not independently measure the CSS findings — read the diff images, not the ratios. **Net: the Phase 2 fix bar is set by H2 (must-fix), then a decision on whether the studio should adopt rem→px to stop lying about H1, then a decision on H3 (move the gallery into the widget pipeline) and H6 (re-validate merged config).**

## Refuted / no-divergence findings

These did not pan out as *user-visible* parity bugs; recording the evidence so they are not re-litigated.

- **H5 — React dev vs prod build is NOT a visual divergence.** Confirmed behavioral-only (`code-read-notes.md` Area A). Prod defines `process.env.NODE_ENV='"production"'` (`config.ts:58`) and minifies; the studio runs React in dev mode (warnings, unminified, error overlay). **Correction to the plan's H5 premise:** the studio *does* run in `StrictMode` (`studio/src/main.tsx:6-10`), so it double-invokes the full `mount()`→`unmount()` lifecycle in `WidgetPreview` (`WidgetPreview.tsx:36-44`) — stressing registry register/deregister, the dispose path, the shared `widgetSheets` cache, and `MPLocalStorageAuth` listener/interval cleanup. The prod IIFE has no StrictMode (`mount.tsx:73,77-89`). This is dev-only and converges to the same single mounted tree — **no DOM/CSS difference**; there is no `NODE_ENV`/StrictMode-keyed rendering branch in widget/runtime code. Document as expected dev behavior; note the studio is the surface where mount/dispose idempotency gets stressed.
- **Injection mechanism (`applyStyles` / `rewriteRootToHost`) — NO DIVERGENCE.** `applyStyles()` (`styling.ts:26`) is the sole CSS-injection sink and the only caller is `mount.tsx:66`; both prod (`autoMount`) and studio (`WidgetPreview`) reach it through the same `mount()`. `rewriteRootToHost` (`theme/src/css.ts:6`) runs unconditionally at `styling.ts:32`, not path-conditional. (`code-read-notes.md` Area B.)
- **`adoptedStyleSheets` vs `<style>` fallback — NO DIVERGENCE (dev vs prod).** It is a **per-browser capability fork** (`supportsConstructable()`, `styling.ts:12-19`), not a dev/prod fork — both studio and prod pick the same branch on the same browser. Cascade is identical: both apply `[widgetSheet, tokenSheet]` in that order (`styling.ts:43` vs `:62`), asserted by `countAppliedSheets === 2` after mount / `=== 0` after dispose in the runtime tests. Only non-visual difference: the constructable path shares one cached `CSSStyleSheet` per widget name; the fallback makes a fresh `<style>` per instance — memory/identity only. (`code-read-notes.md` Area C.)
- **`__PERIMETER_WIDGET_VERSION__` define — NO USER-VISIBLE DIVERGENCE.** Defined only in prod (`config.ts:59`), read only in `entry.ts` (`widgets/*/src/entry.ts:5`). The studio imports `widget.tsx` directly and never loads `entry.ts` (`discovery.ts:49`), so the global is never evaluated in dev → no `ReferenceError`. It is metadata on the definition object, never rendered into the DOM. (`code-read-notes.md` Area D.)
- **API base URL — NO DIVERGENCE.** Identical `https://api.perimeter.org` in both paths; `__PERIMETER_API_URL__` is unset in both (no `define` in `config.ts`, none in studio) → both fall back to the default (`mount.tsx:16-19`). Neither path passes `apiBaseUrl`. (`code-read-notes.md` Area I.)
- **H4 mechanism in *code* — NO DIVERGENCE.** The shadow boundary is identical in both paths (`mount.tsx:63`); inheritable properties cross it the same way in dev and prod. The H4 divergence is purely **environmental** (which host the widget lands in), not a runtime-code fork — see the H4 row above. (`code-read-notes.md` Area H4.)

## Detailed findings

### H2 — `@perimeter/ui` utility classes dropped from the shipped bundle (CSS pipeline) — **headline, must-fix**

- **Evidence:** `css-pipeline-example.md` — "selectors only in dev: 471; …of which attributable to @perimeter/ui: **244**; selectors only in prod: 0." `css-pipeline-sermons.md` — "selectors only in dev: 164; …attributable to @perimeter/ui: **145**; only in prod: 0." The attributed lists are dominated by component-internal utilities: `.bg-primary`, `.bg-destructive`, `.border-ring`, `.focus-visible:ring-ring`, `.placeholder:text-muted-fg`, the entire `input-group`/`tabs-list` `group-*`/`has-[…]` families, `.shadow-md`, `.rounded-md`, `.size-4`, etc.
- **Mechanism:** The widget production pipeline compiles Tailwind with the **widget's own** `tailwind.config.ts`, whose `content` is only `./src/**/*.{ts,tsx}` (`context.md:17`). Classes that appear *only* in `@perimeter/ui` component source (never literally in the widget's own `src`) are not seen by the widget's Tailwind content scan and are purged from the shipped CSS. The studio's Tailwind `content` additionally scans `../widgets/*/src` and `../packages/ui/src` (`context.md:18`), so it generates those classes and the studio preview looks correct. "selectors only in prod: 0" confirms the shipped bundle is a strict subset — nothing is added in prod, things are *missing*.
- **User-visible impact:** A widget composed from `@perimeter/ui` ships with the component's utility styling absent — wrong colors, missing focus rings, collapsed spacing, unstyled groups — while passing the studio eye-test. This is precisely the divergence the studio exists to prevent, so it is the highest-priority fix.
- **Proposed fix (Phase-2-ready):** Add the shared UI source to each widget's Tailwind `content` (`packages/ui/src/**/*.{ts,tsx}`, plus any other workspace package whose components a widget renders), or centralize a `content` preset inside `widgetConfig()` so every widget inherits the same scan set. **Verification:** re-run the CSS pipeline differ for `example` and `sermons`; the "attributable to @perimeter/ui" count must drop to 0 and "selectors only in dev" should collapse to genuine studio-chrome noise. This differ becomes the permanent regression test (spec line 112).

### H1 — rem in dev, px in prod (CSS pipeline)

- **Evidence:** `css-pipeline-example.md` "rem→px value diffs: **2**" — e.g. `.gap-3 gap: dev=0.75rem prod=12px`, `.p-4 padding: dev=1rem prod=16px`. `css-pipeline-sermons.md` "rem→px value diffs: **115**" — e.g. `.mb-4 margin-bottom: dev=1rem prod=16px`, `.size-8: dev=2rem prod=32px`, `.h-10: dev=2.5rem prod=40px`. "value diffs, other: 0" in both — **every** value diff is the rem→px transform; there are no unexplained value differences.
- **Mechanism:** `widgetConfig()` adds the module-private `remToPxPlugin` to the prod PostCSS chain (`config.ts`, `context.md:17`); the studio pipeline has no such plugin (`context.md:18`). So identical Tailwind output is post-processed to `px` in prod and left as `rem` in dev.
- **User-visible impact (inverted):** rem resolves against the root `font-size`. The fixture confirms `html` = 16px but `body` = 19px, and H4 confirms the body value pierces the shadow root, so a `rem` value inside a shipped widget would scale unpredictably against the host. **Prod is correct** — px is immune. The divergence is that the **studio renders `rem` and is therefore the inaccurate surface**: a developer tuning spacing in the studio is tuning against a unit the shipped widget never uses.
- **Proposed fix:** Run the same rem→px transform in the studio pipeline (export and reuse `remToPxPlugin` from `@perimeter/vite-plugin-widget`). Effort S — one plugin in the studio PostCSS config.

### H4 — Host-page inheritable properties pierce the shadow root (host environment)

- **Evidence:** `inheritance.md` — all four probed properties returned **"YES — pierces shadow"**: `font-family` (default `sweet-sans-pro, "Helvetica Neue", Arial, sans-serif` → mutated `cursive`), `font-size` (`19px` → `24px`), `color` (`rgb(53,53,53)` → `rgb(200,0,0)`), `line-height` (`35px` → `60px`). The defaults match the fixture's measured perimeter.org values (`wordpress.html:9-16`).
- **Mechanism:** A shadow root blocks *selector*-based cascade but not CSS *inheritance* of inheritable properties. Tailwind preflight's `html`/`body` resets exist only in the host document, not inside the shadow root (`code-read-notes.md` Area B/H4), so the widget inherits whatever the host page declares for these properties. In dev that is the studio canvas; in prod it is the WordPress page.
- **User-visible impact:** Widget text adopts the host font, size, color, and leading. Confirmed real because the fixture's host values (19px / sweet-sans-pro / #353535 / 35px) differ from a default studio canvas. Combined with H1, a widget that *also* ships `rem` would compound this — but prod's px (H1) isolates spacing from `font-size`, leaving font-family/color/leading as the live inheritance surface.
- **Proposed fix:** Two complementary levers — (1) the studio canvas replicates the host-page values (host-page-sim background, with `packages/parity/fixtures/wordpress.html` as the single source of truth so the audit and the studio never diverge), and (2) the widget base CSS pins the inheritable properties it does not want inherited on `:host`/the widget root. The user decides per property whether inheriting the host font is desirable (brand consistency) or a bug (broken layout).

### H3 — Component gallery light-DOM path (components path)

- **Evidence:** `components-path.md` — "selectors only in dev (studio gallery): **226**; selectors only in prod (shipped widget): 0; rem→px value diffs: **110**." Plus four hand-written structural diffs that the CSS differ cannot see: (a) light DOM vs shadow root, (b) studio preflight + `index.html` base styles leak into the gallery but never cross into a widget's shadow root, (c) tokens delivered as an inline `style` object on a wrapper `<div>` in the gallery vs a `:host` CSS-variable sheet in a widget, (d) the gallery never runs `rewriteRootToHost`. Cross-checked in `code-read-notes.md` Area G: `ComponentPreview.tsx:38,55` renders into a plain `<div>` (no `attachShadow`), bypassing `mount`/`applyStyles` entirely.
- **Mechanism:** `ComponentPreview` is a studio-only introspection surface. It composes the same three root causes as H1+H2 (studio Tailwind content scan + no rem→px) plus the structural light-DOM/token-delivery differences, against a baseline of "how those classes would compile inside a shipped widget."
- **User-visible impact:** **None directly** — there is no prod path that renders `@perimeter/ui` components outside a widget shadow root, so the gallery cannot *mismatch* a shipped render. The harm is that it gives the developer a wrong mental model of how a component looks once shipped (different units, different cascade, different token delivery).
- **Proposed fix:** The spec's `ComponentStage` (spec line 38) — mount gallery examples inside a shadow root via the shared `styling` module, fed CSS through the widget Tailwind preset + rem→px. This makes the gallery parity-correct and folds H3 into the H1+H2 fixes.

### H5 — React dev vs prod + StrictMode (runtime)

See **Refuted / no-divergence** above for the full write-up. Summary: **DIVERGENCE (behavioral-only)** — dev warnings, unminified bundle, dev error overlay, and a studio-only StrictMode double-invoke of the `mount`/`unmount` lifecycle (`code-read-notes.md` Area A; corrects the plan's "no StrictMode in studio" premise via `studio/src/main.tsx:6-10`). No rendered-output difference. Document as expected dev behavior; the StrictMode double-invoke makes the studio the surface where mount/dispose idempotency (registry, `widgetSheets` cache, `MPLocalStorageAuth` listeners/interval) is stressed — a useful property, not a bug.

### H6 — Config/data: studio `configOverrides` seam bypasses zod coercion + validation (config/data) — **behavioral-only, high-attention**

- **Evidence:** `code-read-notes.md` Area E. Prod always runs `parseDataAttrs(host, schema)` then `schema.parse` — the only validation/coercion gate (`mount.tsx:47`, `data-attrs.ts:15,34`); every data-attr value enters as a string (`data-attrs.ts:31`). The studio host carries no `data-*` config attrs (`WidgetPreview.tsx:51`); config arrives via the typed `configOverrides` 4th arg (`WidgetPreview.tsx:39`, from `ConfigPanel.tsx:53,69`), which `mount` merges **after** parse without re-validating: `mergedConfig = { ...parsed.config, ...extras.configOverrides }` (`mount.tsx:49-52`).
- **Mechanism / skipped steps in studio:** (1) kebab→camel name mapping (`data-attrs.ts:30`) never runs; (2) `"true"/"false"`→bool shorthand (`data-attrs.ts:31`) never runs; (3) zod `.parse()` coercion + validation (`z.coerce.number()`, `.int`, `.min/.max`, `.refine`, enum) never runs on override values. The studio is therefore *more permissive* than prod.
- **User-visible impact:** **None on styling/DOM.** But it is a correctness/parity gap: the studio can render config prod would reject (out-of-range value past `.max()`), and a non-coercing schema bug (`z.number()` instead of `z.coerce.number()`) is **invisible in the studio yet throws in prod** when the string data-attr hits `schema.parse`. This is the documented class of bug — the repo guards it deliberately: `data-attrs.test.ts:13,19-21,43-46`, the example/sermons schemas use `z.coerce.*` (`widgets/example/src/widget.tsx:10`, `widgets/sermons/src/types.ts:11,19-40`), and `render.test.tsx:11-12` exists *because* "three studio bugs reached the browser."
- **Proposed fix:** Make the studio config path exercise the same gate as prod — either set real `data-*` attributes on the studio host so `parseDataAttrs` runs, or re-validate `mergedConfig` with `schema.parse` after the merge in `mount` (or a studio-side validation pass). Effort S. Related sub-findings, all behavioral-only and to be **documented** (not code-fixed): studio theme edits use the `updateTokens`/`runtimeOverrides` seam, not prod's `data-theme-*` prefix/validation path (`code-read-notes.md` Area F); CORS from `localhost:5173`→`api.perimeter.org` requires the API allow-list to include localhost (Area I); and a required-auth widget in the studio shows the sign-in stub (and authed calls 401) because the studio origin lacks the WordPress-injected `mpp-widgets_AuthToken` (Area I) — expected dev behavior, not a shipped-code bug.

## Recommended Phase 2 fix bar (proposal for user decision)

**Must fix (ships broken UI today):**
- **H2** — add `packages/ui/src` (and other rendered workspace UI sources) to the widget Tailwind `content`, ideally via a shared `widgetConfig()` content preset. Wire the CSS pipeline differ in as a permanent regression test (spec line 112) so this can never silently regress again. *Effort M.*

**Should fix (the studio is lying to the developer):**
- **H1** — apply rem→px in the studio pipeline so the studio renders the same units the bundle ships. Cheap and removes a whole class of "looked right in the studio" surprises. *Effort S.*
- **H3** — move the component gallery into a shadow-DOM `ComponentStage` on the widget pipeline; folds into the H1+H2 fixes and makes the gallery parity-correct. *Effort M.*
- **H6** — re-validate `mergedConfig` (or route studio config through `parseDataAttrs`) so the studio stops masking prod-only `z.coerce`/validation crashes. Correctness, not pixels, but it is the seam that has historically put bugs in the browser. *Effort S.*

**Accept + document (environmental or expected dev behavior):**
- **H4** — decide per inheritable property whether host inheritance is desired (brand fonts) or pinned (layout safety); replicate host values in the studio canvas via the fixture regardless, so the studio at least *shows* the inheritance. *Effort M; partly a product decision.*
- **H5** — dev warnings / minification / StrictMode double-invoke: document as expected; no code change.
- **H6 sub-findings** — `data-theme-*` vs `updateTokens` seam, localhost CORS, studio auth without the token key: document in the studio dev guide; no shipped-code change.
